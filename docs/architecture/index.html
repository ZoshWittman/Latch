System Overview

Latch is an action-boundary desk that enforces deterministic policies on AI agent tool calls. It provides cryptographic provenance tracking and human-controllable gating for side-effecting operations.

Core Principles

  • Deterministic: Same input always produces same verdict
  • Transparent: Every decision is explainable and auditable
  • Tamper-Evident: Cryptographic binding detects modifications
  • Human-Controllable: HOLD verdicts require explicit human seal
  • Zero Dependencies: No external services required for core operation

Component Details

1. LatchService (Orchestration Layer)

The LatchService is the main orchestrator that coordinates policy evaluation, provenance binding, and persistence.

Responsibilities:

  • Create packets from tool calls
  • Coordinate policy evaluation
  • Bind cryptographic provenance
  • Manage seal operations
  • Verify packet integrity

Key Methods:

createPacket(toolCall: ToolCall): LatchPacket
getPacket(id: string): LatchPacket | null
sealPacket(request: SealRequest): { success: boolean; error?: string }
verifyPacketIntegrity(packetId: string): TamperCheckResult
getPolicies(): PolicyRule[]

2. Policy Engine

Evaluates tool calls against an ordered list of policy rules. First match wins.

Pattern Matching:

  • Exact match: list_dir
  • Partial match: read matches read_file
  • Wildcard: read* matches any tool starting with "read"
  • Case insensitive
  • Searches both tool name and serialized parameters

Spend Cap Enforcement:

If a policy has a spendCap, the engine checks parameters and metadata for spend-related keys (amount, cost, price, spend, value). If any value exceeds the cap, verdict becomes HOLD regardless of the rule's action.

3. Provenance System

Provides tamper-evident binding using SHA-256 hashing.

Hash Construction:

policyHash = SHA-256(normalized(policies))
toolCallHash = SHA-256(normalized(toolCall))
boundHash = SHA-256(policyHash + toolCallHash + timestamp)
Security Model: The provenance system uses deep normalization (sorted keys at all levels) to ensure consistent hashing. Any modification to the tool call, policy set, or binding produces a detectable mismatch.

4. Database Layer

Technology: SQLite with better-sqlite3

Schema:

CREATE TABLE packets (
  id TEXT PRIMARY KEY,
  tool_call TEXT NOT NULL,           -- JSON
  verdict TEXT NOT NULL,              -- OPEN | CLOSED | HOLD
  policy_rule_id TEXT,
  provenance TEXT NOT NULL,           -- JSON
  sealed INTEGER NOT NULL DEFAULT 0,  -- Boolean
  sealed_by TEXT,
  sealed_at INTEGER,
  created_at INTEGER NOT NULL,
  reason TEXT NOT NULL
);

CREATE TABLE policy_rules (
  id TEXT PRIMARY KEY,
  pattern TEXT NOT NULL,
  risk_class TEXT NOT NULL,
  action TEXT NOT NULL,
  spend_cap REAL,
  description TEXT NOT NULL
);

Indexes:

  • idx_packets_verdict - Fast verdict filtering
  • idx_packets_sealed - Fast unsealed HOLD queries
  • idx_packets_created_at - Chronological ordering

Data Flow

Packet Creation Flow

1. Agent submits tool call │ ├─► LatchService.createPacket(toolCall) │ ├─► PolicyEngine.evaluate(toolCall) │ │ │ ├─► Match pattern against rules (first match wins) │ ├─► Check spend cap if defined │ └─► Return verdict + matched rule │ ├─► Provenance.createProvenance(policyHash, toolCall) │ │ │ ├─► Hash policy set │ ├─► Hash tool call │ ├─► Create timestamp │ └─► Bind all together │ ├─► Create LatchPacket structure │ └─► Database.savePacket(packet) │ └─► Return packet to caller

Seal Flow (Human-Only)

1. Human identifies HOLD packet │ ├─► LatchService.sealPacket({ packetId, sealedBy }) │ ├─► Retrieve packet from database │ ├─► Verify verdict === 'HOLD' │ ├─► Verify not already sealed │ ├─► Database.sealPacket(id, sealedBy) │ │ │ └─► UPDATE packets SET sealed=1, sealed_by=?, sealed_at=? │ └─► Return success

Verification Flow

1. Request packet verification │ ├─► LatchService.verifyPacketIntegrity(packetId) │ ├─► Retrieve packet from database │ ├─► Get current policy hash │ ├─► Provenance.verifyProvenance(provenance, policyHash, toolCall) │ │ │ ├─► Recompute tool call hash │ ├─► Compare with stored toolCallHash ─┬─► Mismatch? TAMPERED │ │ └─► Match? Continue │ │ │ ├─► Compare current policy hash ───────┬─► Mismatch? POLICY CHANGED │ │ └─► Match? Continue │ │ │ ├─► Recompute bound hash │ └─► Compare with stored boundHash ─────┬─► Mismatch? CORRUPTED │ └─► Match? VALID │ └─► Return TamperCheckResult

Security Considerations

Threat Model

  • Agent Tampering: Agents cannot modify tool calls post-evaluation (detected by provenance)
  • Policy Bypass: Agents cannot change policies (detected by provenance hash mismatch)
  • Seal Forgery: Only humans can seal HOLD packets (enforced by API/CLI)
  • Database Tampering: Provenance verification detects corruption

Limitations

  • Process Access: If an attacker has process-level access, they can bypass Latch entirely
  • Database Access: Direct database modification can corrupt seals (mitigated by provenance)
  • Policy Definition: Weak policies are the responsibility of the operator
  • Replay Attacks: Latch doesn't prevent replay of legitimate packets

Performance Characteristics

  • Packet Creation: O(n) where n = number of policy rules (stops at first match)
  • Provenance Hashing: O(m) where m = size of tool call + policies
  • Database Operations: O(1) for lookups by ID, O(log n) for indexed queries
  • Verification: O(1) hash comparison operations
Note: Performance is optimized for single-node deployments. For high-throughput scenarios, consider implementing caching or read replicas.

Extension Points

Custom Policy Engine

Implement your own policy evaluation logic by extending PolicyEngine or providing custom PolicyRule arrays.

Database Adapters

The LatchDatabase class can be extended to support other database backends (PostgreSQL, MongoDB, etc.).

Webhook Integration

Add webhook notifications for packet state changes (created, sealed, etc.).

Audit Log Streaming

Stream packet events to external audit systems for long-term retention and compliance.
